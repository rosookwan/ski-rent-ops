# 차량 UI·부분 수거·장비교환·조기반납 개선

2026-09-09. 사용자의 분석 검토 후 승인한 구현·검증·커밋·GitHub Pages 배포 계획이다. 첨부 시안의 문구와 코드는 참고 자료이고, 아래 사용자 요구사항이 우선한다.

## 1. 요청과 확정한 방향

1. `일부만 받았어요`에서는 **실제로 받은 품목과 수량**을 선택한다. 선택하지 않은 물품은 고객에게 남는다.
2. 차량 화면은 Downloads의 `# 스키렌탈샵 UI 개선 7/06 차량 배달·수거.dc.html`을 기준으로 색상, 폰트, 위치, 크기, 간격, 스크롤, 팝업을 맞춘다. 상단 `알림함` 텍스트는 기존 종 아이콘으로 유지한다.
3. POS `추가로 싣기`에는 리프트권만 표시한다. 일반 고객의 배달 장비는 해당 고객 카드의 `실었어요`에서 처리한다. 교환 장비는 고객 상세의 장비교환 업무로 연결한다.
4. 장비교환은 렌탈·반납 상세에서 품목, 수량, 사유, 기존/새 규격, 메모, 처리 방법을 입력한다. 차량 교환이면 배달·수거 목록에 고객과 연결된 업무를 자동 생성한다.
5. 장비 2대 중 1대만 조기반납할 수 있어야 한다. 나머지 대여와 기존 반납 일정은 유지한다.
6. POS 수거 카드에는 `모두 받음`과 `일부만 받음`을 둔다. 차량에서도 같은 의미를 사용한다.
7. 상세 문서를 먼저 커밋하고, 구현은 한 단계씩 검증·커밋·배포한다.

## 3. 공통 수량·업무 원칙

- 새로 지급하는 수량, 고객이 가진 수량, 차량이 수거한 수량, 매장이 확인한 수량을 구분한다.
- 조회, 교환 요청 저장, 수거 예약, 알림 확인만으로 실물 위치를 이동하지 않는다.
- 부분 수거의 대상은 **이번 업무의 아직 받지 않은 물품**이다. 이전에 받은 수량, 다른 고객, 다른 날짜의 예정 물품을 다시 더하지 않는다.
- `받은 수량 = 선택한 실제 물품 수`, `남은 수량 = 이번 처리 전 남은 수량 - 받은 수량`이다.
- 차량 수거는 매장 최종반납이 아니다. 실제 매장 인계 후에 매장 확인 수량이 증가한다.
- 일부만 수거하고 매장에 내린 뒤 다시 수거할 수 있다. 미수거 업무와 고객의 나머지 일정은 계속 남긴다.
- 직접반납한 물품은 기존 차량 수거 대상에서 제외한다. 전량을 직접반납한 경우에만 해당 수거 업무가 완료된다.
- 교환은 추가 대여가 아니다. 기존 장비를 회수하고 대체 장비를 지급해도 대여 세트 수·가격이 증가하지 않는다.
- 부츠·폴대 교환은 스키/보드 본체 반납과 구분한다. 부품 교환을 대여 전체 반납으로 집계하지 않는다.
- 수량과 위치를 바꾸는 명령은 기존 업무 저장소, 버전 검사, 중복 요청 검사, 매장/차량 권한, 이동 이력을 사용한다.
- 저장 도중 실패하면 일부 작업만 남기지 않는다. 양쪽 교환 업무 및 조기수거 일정 분리를 함께 검증한다.

## 4. 부분수거와 POS 조작

### 4.1 받은 품목 선택

- 초기 상태는 전부 미선택, 받은 수량 0이다.
- 품목을 체크하면 그 품목의 이번 대상 전량을 받은 수량으로 채운다. `−/+`로 일부 수량을 조절한다.
- 체크를 해제하거나 수량을 0으로 낮추면 미선택이다.
- 화면에 `이번에 받은 품목`과 `고객에게 남은 품목`을 즉시 함께 표시한다.
- 스키 2대 중 1대: 스키 체크 → 수량 1 → 저장. 고객 보유 1대가 남는다.
- 받은 수량이 0이면 수거 완료를 저장하지 않는다.
- 남은 의류·리프트권을 자동으로 직접반납으로 바꾸지 않는다. 일정/방법 변경은 별도 명시적 조작이다.

### 4.2 모두 받음

- 카드에서 이번 업무의 남은 수량으로 확인창을 채운다.
- 처리 전 품목과 수량을 보여 주고 확인 후 적용한다.
- 모든 고객/차량을 한 번에 처리하는 버튼이 아니다.
- 수거 이후 매장 인계는 기존 `매장에 내리기` 또는 고객 상세의 인수 확인으로 처리한다.

### 4.3 추가 적재

- 매장 보관 리프트권만 후보에 표시한다.
- 다른 차량에 배정된 배달권/환불권은 제외한다.
- 고객 전달용, 예비분, 발권처 환불 대상의 기존 용도를 유지한다.
- 교환품은 교환 고객의 적재 카드에서만 선택한다.
- 하차에는 리프트권뿐 아니라 실제 차량 보관 장비도 계속 표시한다.

## 5. 차량 UI 원본 적용

- 원본 HTML과 폰트·색상 토큰을 기준으로 템플릿을 연결한다. 원본 파일은 수정하지 않는다.
- 보라색 헤더, 업무 필터, 오늘/내일/달력, 네 종류 재고 타일, 변경 요청, 좌측 목록, 우측 상세, 고정 하단 버튼, 보관 내역과 팝업을 유지한다.
- 종 아이콘 알림은 기존 알림함의 읽음·소리·업무 이동과 연결한다.
- 버튼 모양을 가져오는 것과 실제 문자 전송은 별개다. 실제 발송이 연결되지 않은 출발 문자에는 발송됐다는 상태를 만들지 않는다.
- 매장 적재/인계 원본 예시는 실제 이력/보관량이 있는 경우에만 표시한다. 가짜 아침 적재 완료 등을 넣지 않는다.
- 남은 업무, 보관량, 고객 연락처, 방문 순서, 리프트권 유효시간/배정은 기존 저장소에서 읽는다.
- 완료와 일부 완료를 구분하고, 알림 확인은 업무 완료로 해석하지 않는다.
- 픽셀 검증은 동일 브라우저, 화면 크기, 배율 1, Pretendard 로딩 완료, 동일 비교 데이터로 실행한다. 비교용 수량을 실제 앱 샘플에 저장하지 않는다.
- 1366×768, 1024×768, 1440×900, 1920×1080에서 기본/필터/보관/부분/전체 확인/날짜 등 관련 상태를 확인한다.
- 원본 1000px 최소 너비 아래에서는 태블릿 기준 레이아웃을 별도로 축소하지 않고 기존 사용 가능한 화면 경로를 유지한다. 결과 문서에 실제 검증 범위를 기록한다.
- 종 아이콘, 받은 수량 입력, 실제 지원 동작 안내, 교환·조기반납 표시는 의도적 차이로 비교 기준에 명시한다.

## 6. 장비교환

### 6.1 폼

| 필드 | 규칙 |
| --- | --- |
| 고객/접수 | 현재 고객 상세에 고정 |
| 대상 장비 | 고객이 현재 대여 중인 장비/세트에 연결 |
| 교환 품목 | 스키, 스키부츠, 폴대, 보드, 보드부츠, 기타 |
| 수량 | 양의 정수, 해당 대여 및 가능한 재고 한도 확인 |
| 사유 | 파손 교체, 사이즈 변경, 기타 |
| 기존 규격/새 규격 | 별도 입력; 파손 교체 150→150처럼 동일 규격 허용 |
| 메모 | 자동 요약 + 추가 메모; 기타 품목/사유는 설명 필수 |
| 처리 방법 | 매장 교환 또는 차량 배달 |
| 방문 정보 | 날짜, 시간, 장소, 담당 차량; 기존 접수에서 기본값 제공 |

사용자가 세 가지 권장안 적용을 승인했다. 교환품 전달/기존품 회수는 별도 기록, 부츠 한 켤레/폴대 한 조가 수량 1, 교환/조기반납의 금액 자동 변경 없음으로 확정한다.

수량 표기는 사용자가 제시한 `부츠 1개`를 유지하되 부츠 한 켤레/폴대 한 조를 교환 단위 1로 안내한다. 낱짝 단위 교환은 이번에 자동 환산하지 않고 기타 메모로 구체적으로 적는다. 정책을 바꾸면 기존 장비/세트 수량을 자동 재해석하지 않는다.

표시 예:

- `장비교환 · 스키 1대 · 파손 교체 (150 → 150)`
- `장비교환 · 스키부츠 1개 · 사이즈 변경 (255 → 260)`
- `장비교환 · 기타 1개 · 기타 · 고글 밴드 불량 교체`

### 6.2 연결 흐름

1. 교환 요청 저장: 고객, 대상, 사유/규격/메모 기록. 차량 교환이면 교환품 전달과 기존품 회수의 연결된 업무를 생성한다.
2. POS에서 교환품 적재: 가능한 매장 재고 중 지정한 교환품만 차로 이동한다. 부족하면 요청을 남기고 적재를 막는다. 재고를 임의 생성하지 않는다.
3. 차량에서 새 장비 전달/기존 장비 회수를 각각 실제 수량으로 기록한다. 한쪽만 처리했다면 다른 쪽은 미완료로 남긴다.
4. 새 장비를 고객에게 전달한 뒤 원래 대여의 최종 반납 대상과 연결한다. 기존 장비는 교환 회수로 추적하여 이중 반납을 막는다.
5. 매장에 파손품이 들어오면 정상 출고 후보에서 제외한다. 회수했다는 사실과 다시 대여 가능하다는 사실을 구분한다.
6. 고객 상세 변경 이력과 POS/차량 목록에서 같은 교환 사유·규격·상태를 확인한다.

### 6.3 금액 및 예외 처리

- 교환 추가비, 파손 배상액, 고객 환불액 자동 산정.
- 재고 부족 시 존재하지 않는 부츠·폴대·교환 장비 자동 생성.
- 파손품 자동 수리 완료 및 정상 재고 복귀.
- 기존 장비 미회수 상태를 자동으로 반납 완료/분실 종결.

## 7. 일부 조기반납

- 고객 상세의 별도 진입점에서 **실제로 조기반납하는 품목/수량**을 선택한다.
- 사유는 부상, 일정 변경, 기타; 기타는 메모로 설명한다.
- 매장 직접반납: 실제 가져온 수량을 바로 매장 확인하고 남은 대여는 유지한다.
- 차량 수거: 선택한 수량만 새 날짜·시간·장소의 조기수거 업무로 분리한다. 기존 수거 업무에서는 그 물품만 제외한다.
- 이미 수거한 물품은 조기반납 후보에서 제외한다. 진행/일부 처리된 기존 업무를 무조건 취소하거나 다른 고객 물품을 포함하지 않는다.
- 예: 스키 2대 중 1대를 13:00에 조기수거하고, 나머지 1대는 원래 16:30에 수거한다. 의류·리프트권은 선택하지 않으면 유지한다.
- 원래 이용 기간, 요금, 수납액은 자동 변경하지 않는다. 환불 정책은 별도 결정이며 리프트권 발권처 환불 업무와 섞지 않는다.
- 전부 회수했더라도 차량 보관분은 매장 확인 대기로 남긴다.

| 차량 화면 | 같은 물품 ID, 위치, 순서, 고객, 날짜, 메모, 알림을 표시 |
| 매장 직접반납 | 기존 수거 대상에서 선택분만 제외 |
| 차량 수거/매장 인계 | 실물 이동마다 한 번만 집계, 반복 왕복 지원 |
| 리프트권 | 용도/유효시간/고객 배정/환불 업무 보존 |
| 재고 | 추가 적재 후보 제한, 파손품 제외, 부품 교환의 별도 추적 |
| 일정 변경 | 조기수거 분리 뒤 남은 품목의 원래 일정 유지 |
| 알림 | 업무 생성/변경/처리와 연결; 확인 버튼은 재고·업무를 변경하지 않음 |
| 정정/취소 | 이후 이동이 있는 물품은 과거 이력 되돌리기 금지; 교환 연결 보호 |
| 권한/버전 | 담당 차량 외 처리 거절, 구버전 저장 거절, 재시도 중복 방지 |
| 결제/마감 | 교환/조기반납으로 금액·리프트권 회수금 중복 변경 없음 |
| 저장/API | 동일 도메인 명령으로 검증, 메모리 체험과 운영 저장 경계 명시 |

## 9. 구현·커밋·배포 순서

| 단계 | 범위 | 완료 조건 | 상태 |
| --- | --- | --- | --- |
| 0 | 이 요구사항·연결 문서 | 변경 전 근거, 규칙, 보류 사항, 검증 기준 커밋 | 문서 커밋 완료 |
| 1 | POS 리프트권 추가 적재, 모두/부분 수거 | 일부→하차→나머지 수거, 다른 차량/품목 보존 | 로컬 검증 완료 |
| 2 | 차량 시안 적용 + 받은 품목 선택 | 원본 대조, 실제 동작·알림·재고·순서 연결 | 예정 |
| 3 | 장비교환 기록·재고·연결 업무·고객 상세 | 매장/차량/부분/미회수/파손/중복 처리 검사 | 예정 |
| 4 | 일부 조기반납·수거 일정 분리 | 2대 중 1대, 나머지 일정/가격/품목 보존 | 예정 |

각 단계는 관련 테스트 → 필요한 회귀 검사 → 화면 확인 → 해당 파일만 커밋 → main push → GitHub Actions 성공 → 공개 페이지 파일/핵심 동작 확인 후 다음 단계로 진행한다. 원본 시안 파일, 다른 사용자 작업, 계정 설정을 변경하지 않는다.

## 10. 검증·배포 기록

진행하며 단계별 실제 결과와 커밋/Actions/공개 검증을 이 절 또는 연결된 검증 문서에 기록한다. 계획된 검사를 통과한 것처럼 기록하지 않는다.

배포 대상은 기존 GitHub Pages 정적 체험 페이지다. 브라우저 메모리에서 동작하며 새로고침하면 체험 데이터가 초기화된다. 이번 공개 배포를 운영 SQLite API, 실제 기기 간 동기화, 실제 문자·결제·프린터 연결 완료로 표현하지 않는다.
