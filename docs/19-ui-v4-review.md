## 판단

**요청한 화면의 틀은 대부분 마련되어 있다. 다만 그대로 운영 기능에 연결하기 전에 차량 배치와 수량·부분 처리·입력폼·출력 흐름을 수정해야 한다.**

시안의 `CLAUDE.md`는 실제 서버·문자·발권처·프린터 연결을 범위에서 제외한다. 따라서 실제 연결이 없다는 사실 자체를 오류로 판정하지 않았다. 아래에서는 시안 안에서 확인되는 동작 오류, 필요한 UI 보완, 실제 기능 연결 작업을 구분했다.

특히 `fleet-data.js`는 독립된 샘플 엔진이다. 기존 프로젝트에 먼저 구현한 `src/workflows/`와 연결되어 있지 않다. UI를 붙일 때는 이 샘플 엔진의 계산을 운영 코드로 옮기지 말고, [기능 연결 계약](/Users/sookwan/Developer/ski-rent-ops/docs/18-workflow-functions-and-ui-contract.md)의 클라이언트를 사용해야 한다.

## 먼저 수정할 부분

### 1. 차량 1024×600에서 이번 업무의 품목·수량이 가려짐 — 우선 수정

대상: `06 차량 배달·수거.dc.html`

최소 목표 크기 1024×600에서 상단 메뉴가 두 줄로 바뀌고, 집계와 확인 요청 2건까지 표시하면 업무 상세의 스크롤 영역 높이가 약 **97px**만 남는다. 아래 72px 처리 버튼은 보이지만 그 위의 `스키 2 / 의류 2 / 헬멧 1 / 6시간권 2`를 첫 화면에서 읽기 어렵다. 왼쪽 목록도 약 156px라 완료된 첫 카드 하나가 대부분을 차지한다.

수정 방향:

- 고객 이름·장소·이번 품목/수량·완료 버튼은 1024×600에서도 동시에 보이게 한다.
- 상단 집계는 간결한 한 줄 또는 높이가 제한된 두 줄로 정리한다.
- 변경 알림은 중요 요청을 알아볼 수 있는 고정 높이 배너로 줄인다. 우선 확인 요청과 순서 변경을 식별할 수 있어야 한다.
- 완료 업무는 현재 방문 순서에서 빼고 완료 내역에 둔다.
- 메모·리프트권 긴 설명 때문에 핵심 수량이 밀리지 않게 한다.

글자나 처리 버튼 크기를 줄이는 방식으로 해결하지 않는다. 근거: 06의 28~65행, 120~137행, 실제 1024×600 렌더링.

### 2. 리프트권 집계와 추가 적재·매장 인계가 맞지 않음 — 우선 수정

대상: 05 / 06 / 18, `fleet-data.js`

| 재현 | 실제 결과 | 필요한 결과 |
|---|---|---|
| 초기 1호 차량 조회 | 05·06 상단 18매, 05 오른쪽 설명 24매, 18의 차량 보관 합계 17매 | 같은 현재 보관량을 표시 |
| 매장에서 4시간권 2매 추가 적재 | 오른쪽 설명은 24→26매, 상단 4시간권은 5→5매, 전체는 18→18매 | 4시간권과 전체에 각각 +2 |
| 6시간권 3매를 `매장에 내렸어요` 처리 | 스키·의류는 줄지만 6시간권은 7→7매 | 6시간권도 3매 감소 |

원인은 서로 다른 계산이다. `stock()`은 이월 수량과 현재 묶음을 더하고, `liftView()`는 현재 묶음을 보며, 05의 설명은 고객/매장 보관분과 이미 환불된 분까지 묶음 원래 수량으로 더한다. 추가 적재에서 생성한 권에는 `holder`가 없어 현재 보관량에서 제외된다. 매장 인계는 권 묶음의 보관 위치를 바꾸지 않는다.

수정 방향: 모든 화면이 **동일한 실물 이동 기록에서 계산한 차량 집계**를 사용한다. 적재/수거는 입고, 전달/매장 인계/실제 환불은 출고다. 환불 예정은 보관량을 줄이지 않는다. 이월분도 같은 실물 기준에 포함해 중복 합산하지 않는다.

근거: 05의 366~369행, `fleet-data.js` 283~332행·366~399행·451~463행. 브라우저 클릭과 독립 재현 코드 양쪽에서 확인했다.

### 3. 부분 환불의 남은 업무를 계속 처리할 수 없음 — 우선 수정

대상: 06 / 18

차량에 있는 3시간권 묶음에서 2매 환불 업무를 만들고 1매만 환불 처리했다. 차량 수량은 1매 줄어 이 부분은 맞았다. 그러나 화면은 `일부만 환불 완료 · 환불 완료`가 되고 남은 환불 업무 수가 줄어든다. 상세에는 `다음 업무에서 처리`라고 쓰여 있지만 남은 1매를 처리하는 버튼/후속 업무는 없고 `되돌리기`만 남는다.

수정 방향:

- `환불 1매 완료 / 1매 남음`으로 표시하고 남은 수량을 대기 업무에 유지한다.
- `남은 1매 환불`, `이번에는 환불 못 받음`, `남은 환불 예정 취소`를 구분한다.
- 부분 처리된 사실을 취소해야만 나머지를 처리할 수 있는 흐름을 없앤다.
- 같은 규칙을 부분 전달·부분 적재에도 적용한다. 부분 수거의 고객 직접반납 전환은 별도 후속 반납 계획으로 이어져야 한다.

근거: `fleet-data.js` 216행에서 `partial`을 완료로 취급한다. 06의 480~488행·621~639행에는 부분 처리 후 완료 표시/되돌리기만 있다.

### 4. 대표자 등록 → 고객 입력 → 매장 확인 → 출력 흐름이 끊김 — 연결 전 보완

대상: 12 / 13 / 19 / 03 / 04 / 16

12에서 입력 요청은 생성된다. 하지만 `고객이 보는 입력 화면 열기`를 클릭해도 13으로 이동하지 않고 설명 메시지만 표시한다. `준비표 인쇄`도 19로 이동하지 않고 `출력 화면 연결 예정` 창을 연다. 13은 전용 링크의 요청 ID가 아니라 시안 편집 속성의 기본 대표자 `박서윤`으로 자료를 선택한다.

기존 반납 화면 16은 공유 `fleet-data.js`조차 사용하지 않는다. 김영희의 물품을 06에서 회수·재전달해도 16에는 기존 스키 인수/의류 고객 보유/리프트권 미회수 샘플이 그대로 남는다. 04의 김영희 연락처와 05·06의 연락처도 다르다.

수정 방향:

- 고객 입력 링크에 해당 요청을 식별하는 정보를 연결하고, 그 대표자의 이름/연락처를 자동 표시한다.
- 목록→고객 폼→제출 결과→매장 상세→출력 미리보기까지 샘플에서도 실제로 이동하게 한다.
- 전송 요청/고객 제출/매장 확인/출력/준비 완료/실제 지급을 별도 상태로 표시한다.
- 접수·차량·반납·출력은 같은 고객/접수/입력폼 ID를 사용한다.
- 16은 실제 차량 회수·매장 인계·고객 직접반납 결과를 이어받아야 한다. 이미 다음 고객에게 넘어간 권을 이전 고객의 미반납으로 남기지 않는다.
- 공통 메뉴도 통일한다. 현재 05, 12, 17, 18에서 메뉴 항목이 서로 다르고 상당수는 이동 대신 메시지만 표시한다.

이 문제는 실제 문자 업체 연결 없이도 샘플 화면 간 이동과 자료 연결까지 구현할 수 있다. 근거: 12의 500~509행·545~560행, 13의 142~156행, 04/05/06/16 브라우저 표시.

### 5. 인쇄창을 닫아도 고객 변경 알림이 사라짐 — 우선 수정

대상: 12 / 13 / 19

박서윤 상세의 `출력 후 변경됨 / 발 사이즈 240→245`를 확인한 뒤 `준비표 인쇄`를 누르고 안내창을 닫았다. 실제 출력도 매장 확인도 하지 않았는데 변경 표시가 사라졌다.

12의 인쇄 버튼이 즉시 `prepPrint()`를 호출하고, 이 함수가 출력 시각을 덮어쓰면서 `changes=[]`로 지우기 때문이다. 반대로 19의 인쇄 버튼은 미리보기 확인 시각만 기록한다. 두 화면의 출력 상태 정의도 다르다.

또한 출력 후 일행 한 명을 삭제하는 독립 재현에서는 인원이 3→2명으로 줄었지만 변경 내역은 0개였다. 이름을 기준으로 비교하고, 남아 있는 사람만 순회하므로 삭제가 누락된다.

수정 방향:

- 출력 요청, 미리보기, 실제 출력 확인을 분리한다.
- 미리보기/취소로 변경 알림을 지우지 않는다.
- 고객 제출본, 매장 확인본, 실제 출력본을 버전별로 보존한다.
- 일행의 고정 ID로 추가·삭제·이름·장비·사이즈 변경을 비교한다.
- 변경 내용 확인과 준비 완료를 별도 동작으로 둔다.

근거: 12의 500~504행, 19의 299~303행, `fleet-data.js` 652~677행·689~692행.

### 6. 방문 순서에는 완료 업무가 섞이고 초기 시간순도 어긋남

대상: 05 / 06

초기 차량 목록 첫 번째는 08:40 `적재 완료`, 두 번째는 14:20 `매장 확인 대기`다. 실제 남은 수거는 세 번째다. 매장에서도 완료 업무를 위아래로 옮길 수 있다. 초기 목록의 18:30 매장 인계가 18:00 환불보다 먼저 나온다.

수정 방향: 남은 방문 업무만 시간순/매장 지정 순서로 보여주고 완료는 별도 내역으로 둔다. 순서 변경에는 변경자·변경 시각·이전/새 순위를 표시한다. 지금처럼 기존 우선 확인 요청을 별도 알림으로 보존하고 현재 선택 고객도 유지한다. 실제 연결 때 저장 성공·차량 수신·기사 확인을 같은 상태로 취급하지 않는다.

근거: `fleet-data.js` 231~234행·426~447행, 05/06 초기 목록과 두 탭 연동 검증.

### 7. 출력 화면은 기반이 좋지만 팀 식별과 재출력 기준 보완 필요

대상: 19

- A4 20명/장과 21명 분할, 대표자·이름·스키/보드·키·발·의류·체크칸은 확인했다. 11pt 선택 시 이름 글자 크기도 변경된다.
