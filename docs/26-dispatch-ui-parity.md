# 배달·수거 UI와 반복 왕복 처리 검증

2026-09-09

## 기준과 의도적으로 바꾼 부분

기준 파일은 사용자 제공 `# 스키렌탈샵 UI 개선 7/05 배달·수거.dc.html`이다. 파일 SHA-256은 `93e268fcc831b4cbde8bf5003ea75c2776279e7d45f93cadca220f5e2653fbb6`이다. 원본 파일은 수정하지 않았다.

원본의 본문과 리프트권 용도 팝업을 `design/app/dispatch-board.html`로 옮기고, 원본 색상 토큰·Pretendard·폰트 크기·굵기·행간·패딩·간격·모서리·반응형 열 너비를 유지했다. 기존 공통 메뉴와 헤더는 그대로 사용하며, 배달·수거의 헤더 높이만 원본의 64px에 맞췄다. 원본과 앱의 Pretendard 파일 SHA-256은 모두 `9599f12fd42fc0bce1cd50b47a0c022e108d7aa64dd0d1bb0ed44f3282d900b4`이다.

사용자가 차량은 오전에도 여러 차례 매장과 리조트를 왕복하며, 리프트권만 받으러 내려오거나 한 팀의 반납을 여러 번 나눠 수거한다고 설명했다. 이를 반영한 의도적 변경은 다음과 같다.

- ‘아침 / 낮 / 저녁’과 ①②③ 단계 표현을 ‘매장 → 차량 / 방문 순서 / 수거·매장 인계’로 변경했다.
- 왼쪽 ‘추가로 싣기’, 오른쪽 ‘매장에 내리기’를 항상 보이는 하단에 추가했다. 원본의 56px·17px 적재 버튼 규격과 색상을 사용한다.
- 미수거 팀에 ‘수거 수량 입력’을 추가했다. 원본의 48px·16px 보조 버튼 규격을 사용한다.
- 수거 카드에 미수거·차에 보관·매장 인계 수량을 따로 표시한다. 이전 날짜의 미수거 또는 차량 보관분은 오늘 화면에 계속 표시한다.

추가 조작의 기준 HTML 변경은 비교 스크립트에 명시했으며 `reference-adjustments.json`에도 기록한다. 따라서 최종 화면을 **수정하지 않은 원본 전체와 동일**하다고 주장하지 않는다. 공통 셸을 제외한 원본 본문·팝업의 스타일과 배치는 유지하고, 위 조작과 문구만 추가한 기준으로 비교했다. 추가 전의 원본 비교 결과도 `work/dispatch-ui-parity/original-baseline/parity.json`에 보존했다.

## 물품과 업무 처리

- 신규 적재·수거·매장 인계는 기존 물품 ID의 위치를 이동시킨다. 보유량을 다시 만들거나 더하지 않는다.
- ‘추가로 싣기’와 ‘매장에 내리기’는 선택한 1호/2호 차량에 적용하며, 매번 선택한 품목과 수량만 처리한다. 리프트권만 선택할 수 있다.
- 다른 차량의 배달·환불에 배정된 매장 물품은 추가 적재 대상에서 제외한다. 전달 예정 권과 환불 대상 권의 용도도 유지한다.
- 일부 수거 후 차량을 비워도 남은 수거 업무가 유지된다. 전체 수거가 완료돼야 해당 수거 업무를 완료하며, 매장 인계는 별도로 기록한다. 날짜 마감이나 모든 업무 완료를 자동 처리하지 않는다.
- 이전에 매장에 내린 장비를 다시 실어도 옛 수거 건의 ‘차에 보관’ 수량이 되살아나지 않도록 이동 이력과 현재 위치를 함께 확인한다.
- 리프트권 용도 변경은 수량·위치를 보존한다. 환불 예정으로 바꿀 때에는 기존 환불 배정 창을 사용하며 실제 환불액은 생성하지 않는다.
- 수량 창이 열린 뒤 다른 처리가 발생하면 오래된 수량으로 적용하지 않도록 변경 버전을 확인한다.
- 기존 업무 관리의 날짜 조회·완료/취소 내역·순서 변경·우선 확인·차량 업무 이동과 렌탈의 배달 적재 기능을 유지했다.

## 서버와 픽셀 검증

- 앱: `http://127.0.0.1:58148/`
- 원본: 별도 서버 `http://127.0.0.1:58150/`
- 동일 Chrome·배율 1·폰트 로딩 완료·동일 데이터로 비교했다. 비교용 데이터는 브라우저의 독립된 임시 문맥에만 적용했다.
- 해상도: 1024×768, 1366×768, 1440×900, 1920×1080.
- 8개 상태 × 4개 해상도 = **32개 상태**, **1,036개 요소**의 좌표·크기·폰트·색상·패딩·간격·테두리·그림자 측정 차이 **0건**.
- 본문 전체 픽셀의 최대 차이는 **339픽셀 / 0.01806%**, 최대 RGB 채널 차이는 **14/255**였다. 1366×768의 오늘·선택·수거 화면은 차이 **0픽셀**이었다.
- 팝업까지 포함한 원시 픽셀 차이의 최대는 **0.07622%**였다. 다른 공통 헤더가 비치는 팝업의 둥근 바깥 테두리도 원시 비교에 포함해 저장한다. 불투명 내부는 별도로 검사하며, 본문/팝업 내부 전체에서 최대 **0.01806%**, 최대 채널 차이 **19/255**였다. 모든 픽셀이 완전히 같다는 의미는 아니다.
- 비교 기준: 내부 픽셀 차이 ≤0.05%, 채널 차이 ≤40, 측정 요소 차이 0. 원시 이미지·차이 이미지·측정 JSON을 `work/dispatch-ui-parity/`에 저장했다.

재현:

```sh
npm run dev
# 다른 터미널에서 제공된 UI 개선 7 폴더를 58150으로 서비스
python3 -m http.server 58150 --bind 127.0.0.1 --directory '/path/to/UI 개선 7'
SKI_DISPATCH_REFERENCE_DIR='/path/to/UI 개선 7' npm run test:dispatch-parity
npm run test:dispatch-board
```

## 동작과 회귀 검증

- `npm test`: **74/74 통과**.
- `npm run check`: JS 40개, 인라인 스크립트 1개, 정적 빌드 통과.
- `npm run test:dispatch-board`: **17개 통과**, 브라우저 오류·외부 쓰기 요청 0건.
- `npm run test:rental-board`: **12개 통과**.
- `npm run test:navigation`: **6개 통과**.
- POS 4개 해상도와 390px/360px에서 문서 가로·세로 넘침이 없고, 1024px 수거 탭과 고정 하단 버튼이 동작함을 확인했다.

반복 왕복 검증은 전날 미수거 4개 중 2개 수거 → 1개 하차 → 1개 하차 → 남은 2개 수거 → 2개 하차를 화면 버튼으로 실행했다. 매장에 내린 뒤 나머지 수거가 유지되고, 총 실물 수량·다른 물품·다른 업무는 변하지 않았다. 이후 같은 장비를 다시 실어도 과거 수거 보관량에 재집계되지 않았다. 2호 차량에서 리프트권만 1매와 2매씩 추가 적재하고 1매만 하차하는 경우도 검증했다.

## 배포 범위

기존 GitHub Pages 워크플로로 정적 체험 페이지를 배포한다. Pages는 메모리 모드이고 운영 API·SQLite 서버 연결 및 여러 기기 간 실제 동기화는 이번 배포에 포함되지 않는다. 새로고침하면 체험 데이터가 초기화된다.
