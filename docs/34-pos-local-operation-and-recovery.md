# POS 로컬 운영 연결·복구 안내

2026-09-13 · 로컬 API/SQLite 실행과 검증을 위한 안내. 운영 호스트에 배포한 기록은 아니다.

## 화면 실행

프로젝트 루트에서 Node 22.13 이상과 의존성을 준비한 뒤 실행한다.

```sh
npm run build
npm run dev
```

`http://127.0.0.1:58148/`는 체험 화면이다. 같은 브라우저 화면에서 동작하지만 데이터는 메모리이며 새로고침하면 초기화된다. 운영 데이터 검증에는 아래 API 화면을 사용한다.

```sh
SKI_RETURNS_ACCESS_FILE=/absolute/path/access.json SKI_RETURNS_DB=/absolute/path/ledger.sqlite SKI_RETURNS_PORT=58149 npm run returns:server
```

`http://127.0.0.1:58149/pos`에서 직원 인증키로 로그인한다. `access.json`의 기존 서버 계약은 `credentials` 배열이며 각 항목에 `tokenHash`, `shopId`, `actor`가 필요하다. 인증키 원문 대신 SHA-256 해시를 서버 설정에 보관한다. `actor.role`은 `store` 또는 `driver`, 기사는 `vehicleId`가 필요하다. 마감 재개가 필요한 관리자만 `actor.permissions: ["closing.reopen"]`을 설정한다. 인증키나 실제 고객 기록을 Git에 넣지 않는다.

관리 화면의 직원·차량 목록은 업무 기본값이다. 서버의 인증·권한 설정과 자동으로 동일해지는 구조가 아니다. 새 직원 인증은 서버 설정과 함께 확인한다. 서버는 기본적으로 로컬 주소에서만 수신한다. 여러 기기 운영은 HTTPS 호스트·허용 Origin·접근 설정을 확정한 뒤 별도 연결한다.

운영 `/pos`는 임의의 샘플 접수·수량·요금을 만들지 않는다. 처음 사용하기 전 실제 품목·요금·차량·시간·재고를 등록한다. API를 종료하고 다시 실행해도 같은 SQLite 파일을 쓰면 기록을 이어 읽는다.

## 처리 결과가 불명확할 때

1. 다시 새로운 결제·반납을 만들지 말고 **앞선 처리 다시 확인**을 누른다.
2. 동일한 요청번호로 서버 기록을 재확인한다. 이미 성공한 요청은 중복으로 수량이나 돈을 늘리지 않는다.
3. 운영 화면은 미확인 요청을 전송 전에 암호화하여 해당 브라우저에 임시 보관한다. 같은 직원 인증키로 다시 로그인하면 요청을 복구한다. 직원 인증키 원문과 읽을 수 있는 고객·금액 내용을 로컬 저장소에 쓰지 않는다.
4. 브라우저 데이터 삭제·다른 기기·인증키 교체 후에는 로컬 복구 요청이 없을 수 있다. 해당 접수의 처리 이력과 수납 이력을 먼저 확인한다. 서버 기록과 실제 물품·금액을 확인하기 전 같은 업무를 새로 확정하지 않는다.
5. ‘다른 기기에서 변경’ 안내는 **최신 기록 확인** 후 고객과 선택 수량을 다시 확인한다. 입력 중인 접수 초안은 자동으로 덮어쓰지 않는다. 아직 저장하지 않은 일반 접수 초안은 새로고침/종료까지 보존하는 기능이 아니다.

## 백업과 복원

```sh
node scripts/backup-workflows.cjs backup /absolute/path/ledger.sqlite /absolute/path/backups/ledger-20260913.sqlite
node scripts/backup-workflows.cjs inspect /absolute/path/backups/ledger-20260913.sqlite
node scripts/backup-workflows.cjs restore /absolute/path/backups/ledger-20260913.sqlite /absolute/path/restored/ledger.sqlite
```

백업은 SQLite 일관성 스냅샷을 생성하고 무결성을 확인한다. 복원은 **새 파일**로만 수행하며 기존 파일을 덮어쓰지 않는다. 접수·물품·금전·마감·이벤트 개수와 버전을 비교한다. 실제 전환 시 서버를 중지하고 원본과 백업을 보존한 뒤 복원 파일 경로로 다시 시작한다. 데이터 롤백으로 이미 일어난 실제 지급·회수·입금까지 취소되지는 않으므로 장애 시점 이후의 실물과 돈은 별도로 대조한다.

## 기존 자료 이관

`legacy.migrate`는 서버 저장소에서 해당 매장의 원본 접수를 조회한다. 클라이언트가 만들어 보낸 원본을 신뢰하지 않는다. 이관 표식에 원본 버전·비교 지문과 이관 전후 수량·청구액을 남긴다. 같은 원본의 반복 이관은 중복 생성하지 않는다. 이관 후 구 반납 API를 통한 같은 접수 변경은 차단한다.

과거 자료에 개별 단가·수납 기록이 없으면 임의로 복원하지 않는다. 원 청구액과 실물 수량을 보존하고, 이관 전 수납은 확인 필요로 표시한다. 실제 운영 데이터의 샘플 대조와 전체 이관은 별도 실행·인수 대상이다.

## 현장 인수 전에 남은 확인

- 실제 포스 기종·OS·배율·주소창을 제외한 표시 영역, 실물 키보드/터치, 기사 기기.
- 야간 영업일 경계와 현장 요금·할인·보증금·배상·환불 정책. 현재 금전 처리일은 한국 시간의 날짜 경계다. 저장된 야간 설정만으로 날짜 계산이 바뀌지 않는다.
- 실물 프린터 용지·드라이버·출력 결과. 브라우저 요청과 실제 종이 확인을 구분한다.
- 문자 제공자와 실제 송수신, 결제 단말·카드 취소. 현재 UI는 준비 또는 확인한 처리 내역 기록이며 제공자 성공을 임의로 표시하지 않는다.
- 최소 3명의 초기 사용자 과업 관찰, 실제 데이터 이관 대조, 운영 주소·백업 보관·복구 담당자.

검증 결과와 인수 상태는 [구현 검수표](32-pos-workflow-implementation-review.md)를 기준으로 확인한다.
