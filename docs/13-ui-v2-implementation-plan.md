# UI 2차 참고안 구현 준비

작성일: 2026-09-08 · 비교 기준: `7894528` · 상태: 구현 전 비교 기록. 후속 적용은 [UI 2차 적용 기록](14-ui-v2-release.md) 참고

## 적용 범위

최신 요청에 따라 **1024×768 / 1366×768은 PC·POS 화면에만 적용**한다. 고객 모바일 화면과 차량 화면에는 이 두 해상도를 구현 기준으로 강제하지 않는다.

| 유형 | 해당 참고 화면 | 구현·검증 기준 |
|---|---|---|
| PC·POS | 01~05, 07~12, 14, 16 — 총 13개 | 1024×768 / 1366×768, 기본 메뉴 접힘 |
| 차량 태블릿 | 06 | 탭 S6 사진처럼 브라우저 UI가 보이는 낮은 작업 영역도 지원. 1024×520 등 보수적 뷰포트에서 핵심 정보 무스크롤 배치. 기존 1024×800도 유지 |
| 고객 모바일 | 13, 15 | 모바일 폭 360 / 390px. PC에서 열어도 참고안의 최대 폭 390px 유지 |

이번 작업은 참고 화면을 실제로 열어 보고 현재 앱과 비교해 구현 범위를 정리하는 단계다. 앱 소스·원본 참고 파일·GitHub Pages는 변경하지 않았다. 새 반납 UI의 기능 연결과 배포도 후속 구현 단계다.

## 공통 디자인과 레이아웃 규칙

### 폰트·색·컴포넌트

현재 앱과 참고안 모두 Pretendard를 사용한다. 참고안의 실제 계산된 글꼴도 `Pretendard, Apple SD Gothic Neo, Malgun Gothic, system-ui, sans-serif`로 확인했다. 글꼴 교체보다 크기·굵기·행간·여백을 맞추는 작업이 중심이다.

- 기존 [PretendardVariable.woff2](../design/vendor/PretendardVariable.woff2)와 Lucide 아이콘을 재사용한다.
- POS 배경 `#F8F8F8`, 흰색 카드, 테두리 `#E7E7E7`, 카드 모서리 16px. 주색 `#FE4E10`, 본문 `#1A1A1A`, 보조 글자 `#6D6D6D`.
- 일반 POS 제목은 참고안 기준 28px/700, 카드 제목 18~19px, 본문·입력 16px, 보조 설명·표 헤더 14px를 기준으로 화면별 측정값에 맞춘다.
- 일반 주요 버튼 48px 이상, 접수 저장 56px. 작은 표 작업은 참고안의 44px 유지. 차량 주요 버튼은 별도 규칙으로 72px 이상 유지한다.
- 현재 [polish.css](../design/app/polish.css)에 있는 공통 규칙을 정리해 적용한다. 하단에 동일 선택자 덮어쓰기를 계속 쌓지 않는다.

### PC·POS 768 높이 대응

참고안의 일반 POS는 높이 820px 이하에서 본문 패딩을 상하 12px/좌우 14px, 간격을 10px 또는 12px로 줄인다. 02번 지표 카드도 패딩을 줄인다. 현재 앱에는 이에 해당하는 공통 높이 조건이 없다.

- POS 최상위는 `100dvh`, 본문·그리드·카드에는 `min-height:0`을 전달한다.
- 헤더·필터·합계·주요 작업 버튼의 공간을 먼저 확보하고 목록만 스크롤한다.
- 상세 화면은 필요한 경우 본문 안에서 세로 스크롤한다. 모든 상세 정보를 무리하게 768px 안에 압축하지 않는다.
- 높이 조건은 POS 선택자에만 적용한다. `.so-vehicle`, `guest-form`, `guest-guide`에는 적용하지 않는다.
- 원본의 `@media(max-width:1150px)` 접수 규칙과 현재 `1050px` 조건을 정리한다. 1024는 2열, 1366은 3열이 기준이다.
- 원본 접수 2열: 오른쪽 340px, 왼쪽 두 행은 `minmax(320px,1.7fr) minmax(240px,1fr)`. 현재의 상품 최소 600px·반납 최소 350px 규칙은 이 기준과 맞지 않는다.
- 접수 상품 영역은 낮은 높이에서 기간 선택과 상품 타일을 함께 스크롤한다. 타일 안에 불필요한 중첩 스크롤을 만들지 않는다.

### 메뉴

- 매장 메뉴는 기본 72px 아이콘 레일, 펼침 214px. 메뉴 이동 후 다시 접히는 현재 동작을 유지한다.
- `반납 확인`을 `렌탈현황` 다음에 넣고 모든 POS 화면에서 같은 메뉴를 사용한다. 참고 파일 중 16번에만 새 메뉴가 있어 원본 파일 간 메뉴 목록이 다르다.
- [core.js](../design/app/core.js)의 `routes.slice(0,6)` 구분은 새 메뉴 추가 시 함께 수정한다. 주요 업무 7개/관리 5개가 되므로 그룹을 명시하면 누락을 줄일 수 있다.
- 접힌 아이콘은 접근 가능한 이름과 설명을 유지한다. 펼친 메뉴 및 맨 아래 QR 메뉴도 내부 스크롤로 접근 가능해야 한다.

### 차량: 좁은 태블릿에서도 현재 업무를 한눈에 표시

2026-09-08 사용자 추가 요구: 탭 S6의 브라우저 탭·주소창·하단 작업 표시줄이 보이는 상태에서도 한눈에 업무를 확인할 수 있어야 한다. 이후 앱 형태로 전환하더라도 이 좁은 환경을 계속 지원한다. **POS의 1024×768/1366×768 조건과 별개의 차량 요구사항**이다.

#### 첨부 화면과 현재 앱에서 확인한 현상

- 사진 1/4의 간단 모드는 장소·고객 일부와 버튼이 보이지만 시간·연락처·장비 수량을 함께 볼 수 없다.
- 사진 2/4의 상세 모드는 우선 확인 알림·장소·시간이 보일 때 고객·품목 수량이 아래로 숨는다.
- 사진 3/4와 4/4는 같은 배달 업무를 스크롤한 위치에 따라 장소 또는 품목 수량이 따로 보이는 상태다. 버튼만 고정되어 있어도 작업 대상 수량을 동시에 확인할 수 없는 것이 핵심 문제다.
- 사진의 외곽 검은 영역·이전/다음 화살표는 카카오톡 이미지 뷰어이며 차량 앱 레이아웃에 포함하지 않는다.
- 현재 앱을 **1024×520 CSS 뷰포트**로 열어 간단·상세 모두 핵심 정보가 잘리는 현상을 재현했다. **1024×650**으로 높이를 늘려도 우선 확인 알림이 있는 상세 모드의 품목 수량은 아래로 숨었다.
- 이 두 크기는 사진 상황을 보수적으로 재현한 검사값이다. 이미지가 리사이즈되어 있으므로 실제 탭 S6의 CSS 뷰포트·화면 배율을 사진으로 확정한 값은 아니다.

원인은 [polish.css](../design/app/polish.css)의 큰 고정 영역과 상세 모드의 세로 배치다. 헤더 88px, 필터 52px, 우선 확인 알림 최소 76px, 작업 버튼 72px에 각각 패딩·간격이 더해진다. 간단 모드에는 다음 일정도 들어간다. 나머지 공간을 `.ski-visit-inner`의 `overflow:auto`로 처리하고, 상세 모드는 장소/시간과 고객/장비를 세로로 쌓는다. 바깥 화면이 `100dvh`여도 핵심 내용의 내부 스크롤은 남을 수 있다.

#### 차량 배치 원칙

1. **두 모드 공통으로 동시에 보일 정보**: 배달/수거 구분, 장소와 만나는 위치, 날짜·약속 시간/타임, 고객 이름·연락처, 현재 방문 대상의 품목별 수량, 우선 확인 요청, 작업 버튼. 스크롤이나 모드 전환을 해야 이 정보를 확인하는 상태를 완료로 보지 않는다.
2. **상단 압축**: 낮은 높이에서는 제목·차량·모드 전환을 약 56~64px 안에 배치한다. 필터·날짜·정렬은 44~48px 한 줄로 정리한다. 핵심 정보를 줄이기 전에 장식 여백과 반복 설명부터 줄인다.
3. **알림 유지**: 우선 확인 요청은 짧은 가로 띠와 44px 이상의 확인 버튼으로 표시한다. 자동으로 확인 처리하거나 알림을 감춰서 공간을 확보하지 않는다.
4. **본문 가로 배치**: 장소/시간과 고객/품목 수량을 나란히 배치한다. 상세 모드도 낮은 높이에서 긴 세로 카드로 쌓지 않는다. 장소와 시간의 큰 여백을 줄이고 품목은 여러 열의 수량 카드로 표시한다.
5. **작업 버튼**: 전화·출발 문자·일부 반납·전체 수거를 72px 이상으로 유지한다. 배달 업무에는 해당 배달 동작을 표시한다. 버튼을 고정할 때 본문 위에 덮지 않도록 실제 공간을 확보한다.
6. **일정 목록**: 상세 모드는 목록 폭·행 높이를 줄여 샘플 3건을 한눈에 표시한다. 건수가 많을 때는 별도 목록 페이지 이동을 사용해 현재 업무 카드가 길어지지 않도록 한다. 간단 모드의 다음 2건은 시간·장소를 담은 짧은 가로 카드로 배치한다.
7. **넘치는 상세 정보**: 긴 보조 메모·과거 이력 등은 명시적인 상세 보기로 분리한다. 고객 연락처나 품목별 수량을 생략하거나 합계만 보여주는 방식으로 맞추지 않는다. 긴 장소명·최대 품목 조합으로 별도 검증한다.
8. **사용 가능 높이 대응**: 차량 화면에만 높이 조건 또는 컨테이너 조건을 적용한다. 실제 앱 뷰포트와 시스템 안전 영역을 기준으로 계산하며, 브라우저 상단 높이를 임의의 상수로 다시 빼지 않는다. `overflow:hidden`이나 화면 전체 축소만으로 내용이 잘린 상태를 통과시키지 않는다.

압축 모드의 첫 설계 범위는 가로 태블릿의 사용 높이 약 680px 이하로 잡고 실제 배치에 맞춰 조정한다. 위의 높이 수치는 구현 전 설계 목표이며 아직 적용·검증된 수정값이 아니다. 높이가 충분하면 기존의 여유 있는 배치로 돌아간다.

#### 앱 형태로 바뀌는 경우

설치형 웹앱의 `standalone` 표시 모드는 브라우저의 탭·주소창을 제외해 사용 공간을 늘릴 수 있다. 상태표시줄·시스템 뒤로가기 같은 영역은 남을 수 있으므로 앱 전환이 곧 전체 화면이나 스크롤 해소를 뜻하지는 않는다. [W3C 표시 모드 정의](https://www.w3.org/TR/appmanifest/#display-member)

네이티브 앱도 상태표시줄·탐색 영역을 고려해 내용을 배치해야 한다. 시스템 바 뒤까지 배경을 그리는 것과 중요한 내용을 가리지 않는 것은 별도 조건이다. [Android 시스템 영역 처리](https://developer.android.com/develop/ui/views/layout/insets)

따라서 **브라우저로 사용하는 좁은 상태에서도 핵심 정보 무스크롤 → 앱으로 실행하면 확보된 공간 활용**을 기준으로 한다. 앱 설치·전체 화면 전환·태스크바 숨김을 사용 전제조건으로 요구하지 않는다. 이번 단계에서 앱/PWA 전환을 구현한 것은 아니다.

## 반납 UI를 연결하기 전 정리할 계약

기능 본체는 [반납 기능 계약](10-return-functions.md), [UI 연결 지침](11-return-ui-handoff.md), [return-runtime.js](../design/app/return-runtime.js)에 이미 있다. 현재 `SkiOps.returns`는 별도 가상 접수 2건을 사용하며 기존 `R-021` 등의 화면 데이터와 자동 연결되어 있지 않다.

### 새 디자인과 기존 모듈의 차이

| 항목 | 참고 화면 | 현재 모듈 | 구현 시 처리 |
|---|---|---|---|
| 수량 정정 | 확인 완료 총량에서 ‘되돌릴 수량’을 선택해 고객 보유로 이동 | `movementId`별 실제 받은 **새 총수량**으로 정정 | 먼저 변경 이력에서 대상 기록을 선택. 기존 수량·정정 후 수량·변경 결과를 보여주고 명령 생성. 참고안의 차감량을 그대로 보내지 않음 |
| 차량 인수 최종 확인 | 품목별 대기 총량 표시 | 인수 기록의 `collectionId`별 미확인량 확인 | `pendingConfirmations`를 바탕으로 인수 기록을 식별. 여러 번 수거된 품목을 하나의 임의 기록에 합치지 않음 |
| 차량 확인 취소 | 고객 보유로 되돌리는 단순 설명 | 매장 확인 기록을 줄이면 해당 수량은 차량 보유로 돌아감 | 이동 경로별 결과를 미리 표시. 차량 인수 취소는 후속 매장 확인의 종속 관계를 지킴 |
| 08 회수 매수/금액 | 매장 확인 완료분만 회수, 차량 인수분은 미회수 | `recoveredQuantity`/`recoveryValueWon`은 최초 차량 인수 또는 직접반납 기준 | 기존 회수 필드를 그대로 08번에 표시하면 틀림. 매장 확인 기준 수량·금액을 별도 표시 모델로 산출 |
| 08 과거 날짜 | ‘9/8 마감 시점’이라고 표시 | `current*`는 조회 시점 잔량, 기간 집계는 최초 회수일 기준 | 날짜별 마감 시점 잔량을 쓰려면 시점 조회/이력 재구성이 필요. 현재 잔량을 과거 확정 마감으로 표시하지 않음 |
| 샘플 접수 | 파일별 독립 샘플·서로 다른 진행 시점 | 기존 UI 원장과 반납 체험 원장 분리 | 화면 간 공유할 데모 ID·품목·실제 지급량·수거·매장 확인 이력을 명시한 데이터 매핑을 먼저 작성 |

특히 04·06의 김영희 샘플은 스키 2/의류 2/헬멧 1을 보여주며, 16은 스키 2/의류 2/리프트권 2를 기준으로 한다. 04의 이수진은 대여 중, 16은 반납 완료다. 파일별 화면을 그대로 복사해 같은 고객의 일관된 상태로 간주하면 안 된다.

리프트권은 아직 지급하지 않은 수량을 미회수로 올리지 않는다. 회수 대상 수량과 구매/일별 사용 수량도 구분한다. 기본 반납일을 무조건 다음 날로 설정하지 않으며, 참고 샘플의 날짜를 운영 규칙으로 해석하지 않는다.

### 연결 대상

- 03 접수: 실제 지급 예정 수량과 일별 사용량을 구분해 `create`/`issue`에 전달. 품목별 반납 계획은 `{method,date,time,slot,place}`를 사용한다.
- 06 차량: 현재 방문 대상 수량과 못 받은 품목을 `prepareVehicleReturn`에 전달하고 `collect`로 처리한다. 다른 날짜의 리프트권은 전체 수거에 포함하지 않는다.
- 16 목록: `list({onDate,filter})`, `dueItems`, `pendingConfirmations`를 사용한다.
- 16 직접반납: 고객 보유량 범위에서 `receiveDirect`. 차량 확인은 `confirmVehicle`, 예정 변경은 `planReturn`.
- 16 이력: `history`, `correctReturn`, `undoReturn`. 상태·완료 여부는 명령 응답을 받은 뒤 갱신한다.
- 중복 클릭은 같은 요청 ID로 처리하고 버전 충돌은 최신 내역을 표시한다. 충돌 시 자동으로 재실행하지 않는다.
- 08 집계: 매장 확인 기준 표시 모델과 현재 잔량/선택 기간 집계를 분리한다. 기준 금액은 고객 환불이나 실제 수납에 더하지 않는다.

기존 메모리 모듈을 통한 화면 체험과 운영 API 연결은 별개다. UI 이식 때 SQLite 서버나 실제 문자·결제·인증을 함께 활성화하지 않는다.

## 참고안 그대로 옮기지 않을 부분

- 1024 POS의 여러 목록에서 오른쪽 작업 열은 가로 스크롤 후 보인다. 문서 전체 넘침은 없지만 작업 접근성은 구현 후 다시 확인한다. 글자를 과도하게 줄이기보다 내부 가로 스크롤을 유지하고 필요한 경우 작업 열 고정을 검토한다.
- 03의 1024 헤더는 일부 보조 버튼 문구가 두 줄로 내려간다. 대표자와 주요 작업을 우선하고 보조 버튼 폭·간격을 정리한다.
- 12·16 상세는 1024에서 요약이 아래로 내려간다. 내용 스크롤은 허용하되 주요 반납 버튼에 도달할 수 있어야 한다.
- 15의 바로가기 이동 후 고정 상단에 섹션 제목 일부가 가려지는 장면이 있었다. 해당 내부 스크롤 컨테이너에 맞는 이동 여백을 적용한다.
- 참고안의 화면 이동 안내·예시 버튼은 현재 앱에 이미 연결된 메뉴/상세 동작을 대체하지 않는다.
- 입력폼 설정에 있는 헬멧·메모 항목과 실제 고객 입력 단계의 필드 구성은 별도 연결 확인이 필요하다. 설정 화면이 있다는 이유로 고객 폼까지 자동 반영됐다고 간주하지 않는다.

## 순차 구현 계획

1. **공통 기반**: POS 전용 768 높이 규칙, 글꼴·컨트롤·카드 토큰, 72px 접힌 메뉴, 표 스크롤 규칙 정리. 반납 데이터/정정/집계 계약 차이 해소안을 먼저 확정한다.
2. **01~05**: 로그인→오늘 현황→접수→렌탈현황·상세→배달·수거 순서. 각 화면을 두 POS 해상도에서 확인한 뒤 다음 화면으로 이동한다.
3. **06**: 차량 전용 스타일과 일부 반납 흐름. 탭 S6 사진처럼 낮은 작업 영역부터 간단·상세의 핵심 정보 무스크롤 배치를 맞춘 뒤 기존 1024×800을 확인한다. 앱 전환을 해결의 전제로 삼지 않는다.
4. **07~11**: 거래처→마감→고객→재고→설정. 리프트권 회수 탭은 앞서 정한 표시 기준을 사용한다.
5. **12~15**: 사전 준비→고객 입력→QR 관리→고객 안내. PC와 모바일 스타일을 분리해 진행한다.
6. **16**: 새 반납 목록·상세·팝업 및 이력 연결. 03/04/05/06/08에서 같은 접수 상태를 표시하도록 통합한다.
7. **통합 확인**: 아래 완료 기준을 검증하고 구현 결과를 정리한다. Pages 반영은 실제 구현 작업의 완료 단계에서 진행한다.

## 구현 완료 기준

### 화면

- PC·POS 13개 × 2크기 = 기본 26조합. 접힘/펼침 메뉴, 목록의 첫/마지막 행, 가로 스크롤 끝의 작업 버튼도 확인한다.
- 03: 대표자 팝업, 1/2/5일, 장비·리프트권, 할인 적용, 실제 수량, 품목별 반납 펼침, 긴 내역에서도 합계·저장·견적이 보인다.
- 02: 금액·단위가 깨지지 않고 차량 카드가 하단 바로가기에 겹치지 않는다.
- 표의 가로 스크롤은 패널 내부에 한정하며 열 헤더와 본문이 일치한다. 1024에서 여러 줄이 되더라도 고객·상태·작업을 식별할 수 있다.
- 모달은 화면 안에 닫기·확인 버튼을 제공하고 긴 내용은 모달 내부에서 스크롤한다. 키보드 포커스와 닫은 뒤 복귀도 확인한다.
- 06은 POS 26조합에 넣지 않는다. 위 차량 전용 검증 행렬에서 장소·시간·고객·연락처·품목별 수량과 72px 작업 버튼이 동시에 보이는지 확인한다. 일부/전체/전혀 못 받은 경우도 확인한다.
- 13·15도 POS 26조합에 넣지 않는다. 360/390px 모바일에서 고정 버튼, 가로 넘침, 긴 일행 목록, FAQ 이동·접힘을 확인한다.
- 기존 1440×900 / 1366×1024 / 1920×1080 PC 화면도 간격과 메뉴 회귀를 확인한다.

### 기능과 상태

- 대여 기간·일별 수량·할인·최종 금액은 UI 변경 전후 동일한 입력에서 동일하게 계산된다.
- 직접반납/차량 인수/매장 확인을 구분하고, 잔량 또는 추가 지급 대상이 있으면 전체 반납 완료로 표시하지 않는다.
- 오늘 일부 수거→의류 직접반납→리프트권 내일 계획→차량 인수분 매장 확인→다음 날 리프트권 반납→정정 흐름을 같은 접수로 확인한다.
- 여러 인수 기록, 수량 초과·0·음수, 두 번 클릭, 오래된 버전, 확인 취소 후 재처리를 확인한다.
- 리프트권 회수 탭은 차량 인수 전/후·매장 확인 전/후·다음 날 확인·과거 기록 정정에서 정해진 기준과 맞는다.
- 검색·탭·상세·뒤로가기·손님 공개 링크·QR 이미지 연결을 유지한다.

기존 검증 도구는 [visual-check.cjs](../scripts/visual-check.cjs), [smoke.cjs](../scripts/smoke.cjs), [반납 테스트](../tests/)를 확장한다. 현재 시각 검증에는 새 POS 크기가 기본 행렬로 들어 있지 않으므로 추가가 필요하다. 이번 준비 단계에서는 기존 테스트의 과거 통과 기록을 새 구현의 통과로 취급하지 않았다.

참고 서버의 현재 58149 포트는 로컬 반납 API 기본 포트와 같으므로, 후속 API 검증 시 참고 서버 포트를 분리한다. 현재 실행한 것은 정적 참고 서버와 앱 미리보기뿐이다.
