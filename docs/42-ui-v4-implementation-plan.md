# 42. POS UI v4 구현 계획서 (2026-09-21)

상태: **구현 중** (2026-09-21 시작 · 브랜치 `feat/pos-ui-v4`). 힉스필드 시안 46장(`docs/38` · `docs/40` · `docs/41`)의 방향을 실제 앱(`design/app`)에 옮기는 순서와 기준을 정한다. 이 문서는 진행하면서 계속 고쳐 쓰는 문서다(11절 진행 기록, 12절 결정 기록).

## 0. 한눈에

- **무엇을**: 포스 화면 전체를 "큰 글자 · 잘린 글자 0 · 스크롤 0 · 한눈에" 기준으로 다시 다듬는다. 업무 규칙과 저장 방식은 그대로 두고 **화면만** 바꾼다.
- **어떤 순서로**: 검사 도구(M0) → 글자·공통 셸(M1) → 카드·목록(M2) → 오늘 할 일·정산(M3) → 새 접수·접수 상세(M4) → 팝업(M5) → 관리(M6) → 기사 태블릿·휴대폰(M7) → 마무리·반영(M8).
- **어떻게 확인하나**: 단계마다 화면을 실제 크기로 촬영하면서 **글자 크기 · 잘린 글자 · 반쯤 잘린 카드 · 버튼 높이 · 스크롤**을 기계로 센다. 목표는 전부 0건이다. 기존 업무 검사(지급·반납·수납 등)는 그대로 통과해야 한다.
- **반영**: 작업은 브랜치에서 하고, 공개 체험판(Pages)과 `main` 반영은 단계가 끝날 때마다 확인을 받은 뒤에만 한다.
- **정해진 것**: 10절의 1~5번과 7번은 2026-09-21에 추천안으로 확정했다. 6번(매장 포스의 실제 표시 영역)만 M1 뒤에 읽어 주시면 된다.

## 1. 목적과 범위

| 구분 | 내용 |
|---|---|
| 목적 | 사용자 요구 5가지(`docs/38` 1절): 포스에서 쓰기 편할 것 · 낮은 해상도에서 글자 잘림 0 · 스크롤 최대한 없애기 · 한눈에 보기 · 나이 있는 사용자 |
| 범위 | 공통 셸(레일·헤더·필터 줄·하단), 목록 화면(접수·준비·이용·반납·리프트권·차량 운행), 오늘 할 일, 정산·마감, 새 접수·일행·장비 추가, 접수 상세, 팝업 전체, 관리 8화면, 기사 태블릿·휴대폰 |

시안에 없는 기존 기능(헤더의 `고객 찾기`, 재시도 버튼, 연결 상태 표시 등)은 없애지 않는다. 시안은 배치의 방향이고, 기능의 기준은 지금 앱이다.

## 2. 기준 (고정값)

### 2-1. 표시 영역

| 대상 | 필수 | 함께 검사 | 근거 |
|---|---|---|---|
| 매장 포스 | 1024×600 · 1024×768 · 1366×768 | 907×648(낮고 좁은 창), 875×600(가장 빡빡한 시험값) | `docs/30` R04 · `docs/35` 6절 · `docs/38` 7-3 |
| 기사 태블릿 | 1024×520 · 1024×600 | 1280×720 | `docs/37` 9절 |
| 기사 휴대폰 | 360×640 | 390×740 · 412×780 | `docs/41` 1절 |

숫자는 모니터 해상도가 아니라 브라우저 안의 **실제 앱 표시 영역**이다. 매장 포스의 실제 값은 아직 재지 못했다(10절 6번).

### 2-2. 글자와 누르는 곳

| 항목 | 포스 | 기사 태블릿 | 기사 휴대폰 |
|---|---|---|---|
| 가장 작은 글자 | 16px | 16px | 16px |
| 본문 · 이름/제목 · 핵심 숫자 | 18 · 22 · 32~40px | 같음 | 18 · 22 · 32px |
| 누르는 곳 최소 높이 | 52px | 56px | 52px |
| 주 버튼 | 56px | 72px | 64px(폭 전체) |
| 레일 | 112px(폭 1000px 미만은 96px), 라벨 16px | 없음 | 없음 |
| 헤더 · 필터 줄 · 하단 | 60 · 60 · 72px | 60 · 60 · 80px | 56 · 60 · 72px |

알림 종의 빨간 숫자 점만 16px 미만을 허용한다.

### 2-3. 글자를 자르지 않는 규칙 (`docs/38` 7-5 · 7-6)

1. 카드·행의 글자는 **한 줄**이고 말줄임표(…)를 쓰지 않는다.
2. 자리가 모자라면 덜 중요한 조각부터 **통째로** 뺀다(전화번호 → 접수번호 → 이용일). 품목은 들어가는 종류까지만 적고 `외 N종`으로 끝낸다. 빠진 내용은 접수 상세에서 본다.
3. 뺄지 말지는 글자 수가 아니라 **그 자리의 실제 폭으로 재서** 정하고, 창 크기가 바뀌면 다시 잰다.
4. 쪽 나눔은 **높이로 계산**한다. 온전히 안 들어가는 카드·행은 다음 쪽으로 넘기고, 쪽수(`‹ 1 / 2쪽 ›`)는 하단 바에 둔다.
5. 목록 영역이 낮아 묶음 제목 2개가 안 들어가면(높이 640px 미만) 쪽마다 제목을 한 줄만 두고 시간대를 함께 적는다(`09:00~12:00 · 12:00~17:00 수령`).
6. 기사 휴대폰에서 긴 팀 이름·장소는 그 줄만 두 줄로 늘린다(`docs/41` 4절).

### 2-4. 이미 정한 것

- 목록은 **카드**로(행 목록 + 상세 패널 안은 채택하지 않음). 기사 화면만 행 목록이다.
- 카드는 네 줄: 이름·전화·상태 / 시간·장소·접수번호 / 품목 + 상태 칩 / **금액과 버튼 한 줄**. 높이 171px 고정.
- 헤더는 모든 화면에서 같다: `스키노트` · 매장명 · 화면 제목 · 상태 알약 · 알림 종 · `나가기`.
- 주 동작 버튼은 주황 바탕 + 흰 글자, 화면마다 한 종류. 기사 화면은 보라.

## 4. 구현 방침

1. **제자리에서 고친다.** 번들이 1,511,218바이트로 한도(1,750,000 · `scripts/build.py:66`)의 86.4%다. v3용·v4용 파일을 나란히 두면 한도를 넘는다. 기존 `pos-*.css/js`를 고치고, 단계마다 번들 크기를 적는다(목표 1,650,000 이하).
2. **화면 약속을 지킨다.** 검증 스크립트가 쓰는 id·클래스·`data-action`·`data-pos-input`·버튼 문구(부록 A)는 그대로 둔다. 흐름이 바뀌어 어쩔 수 없을 때는 **같은 커밋에서** 스크립트를 함께 고친다.
3. **`[data-pos-scroll]`은 남긴다.** v4의 카드 영역은 스크롤하지 않지만(넘치는 것은 다음 쪽), 검사 4개가 "이 표시가 없는 곳은 스크롤 금지"를 확인하므로 속성은 유지한다.
4. **부품 먼저.** 셸·카드·쪽 나눔·팝업을 `pos-shell.js/css`의 공통 부품으로 만들고 화면은 그것을 쓴다. 포스 화면 코드(`pos-*.js/css`)는 약 2,200줄로 작고 공통 부품 의존도가 높아서, M1~M2가 끝나면 대부분의 화면이 함께 바뀐다.
5. **글자 맞춤 도우미(`P.fit`)**: 조각 목록과 우선순위를 받아 실제 폭(canvas 측정)으로 한 줄을 만든다. 글꼴이 준비된 뒤와 창 크기가 바뀔 때 다시 맞춘다. 한 쪽에 보이는 카드(최대 6장)만 재므로 100팀이어도 느려지지 않는다.
6. **높이 쪽 나눔(`P.cards` · `P.pager` 공통)**: 지금은 모듈마다 `innerHeight < 700 ? 3 : 4` 같은 구간값을 쓰고 창 크기 변화에 반응하지 않는다(`pos-orders.js:4` 등 9곳). 목록 영역의 실제 높이와 카드·행 높이로 계산하는 한 가지 방식으로 바꾼다.
7. **저장소·통신 API 금지는 그대로.** `design/app/*.js`에는 `fetch` · `localStorage` 등을 쓸 수 없다(`scripts/check.py:8`). 쪽 번호 같은 화면 상태는 지금처럼 메모리에 둔다.
8. **새 파일은 빌드 목록에 직접 넣는다**(`scripts/build.py:10` JS, `:52` CSS). 브라우저 검사는 `scripts/`에 두고 `tests/workflows-*.test.cjs` 이름을 쓰지 않는다(Pages CI가 브라우저 없이 그 글롭을 돈다 · `docs/37` 8절).

## 5. 단계

크기는 고치는 양의 어림이다(S 작음 · M 보통 · L 큼). 각 단계는 끝날 때 6절의 검사를 통과하고 커밋한다.

### M0 · 검사 도구와 기준선 (S) — 화면은 안 바뀜

- `scripts/capture-pos-release.cjs` · `capture-pos-driver.cjs`: 출력 폴더와 제목을 바꿀 수 있게 하고(v3 촬영본 `docs/pos-ui-v3`을 덮어쓰지 않게 → `docs/pos-ui-v4`), 907×648을 추가한다.
- 촬영할 때 다섯 가지를 함께 센다: ① 16px 미만 글자 ② 폭을 넘어 잘린 글자 ③ 목록 영역 아래로 반쯤 잘린 카드·행 ④ 52px 미만 누르는 곳 ⑤ 허용되지 않은 스크롤. 결과는 `screens.json`에 남는다.
- `npm run pos:rules`(신설): 위 다섯 가지가 0이 아니면 실패. 단계별로 적용 범위를 넓힌다(처음에는 보고만).
- v3 상태로 한 번 돌려 **기준선**을 `docs/pos-ui-v4/baseline.json`과 11절에 적는다. 기존 검사(`test:pos:*`)도 지금 통과하는지 먼저 확인해, 원래 깨져 있던 것과 v4 때문에 깨진 것을 구분한다.
- 완료 기준: 기준선 기록, 기존 검사 현황 기록.

### M1 · 글자·크기 기준과 공통 셸 (M)

- 고칠 곳: `pos-shell.css`(토큰 `:2`, 레일 `:4~16`, 헤더 `:20`, 필터 줄 `:54~60`, 하단 `:68~70`, 버튼 `:75`), `pos-shell.js`(`navigation :25`, `header :40`, `page :59`), `pos-orders.css`, `pos-keypad.css`, `pos-management.js:187~190`.
- 2-2의 값을 CSS 변수로 정의하고, 16px 미만 글자(레일 14px, 배지 14px, 메타 15px 등 15곳)와 48px 높이(9곳)를 변수로 바꾼다.
- 레일 112px·라벨 16px·아이콘 26px(폭 1000px 미만 96px), 관리 레일 7개도 같은 규격. 헤더에 `스키노트`·상태 알약·종·`나가기`를 같은 자리에.
- 필터 줄: 검색 + `오늘/내일/전체` + `달력` + 정렬 하나, 칩 52px. 주 버튼은 주황 바탕 + 흰 글자(지금 카드 버튼은 연주황 바탕이라 대비가 낮다).
- 스크립트 안에 들어 있는 관리 화면 스타일(`pos-management.js:187~190`)을 CSS 파일로 옮기고, 마크업의 인라인 스타일(`pos-orders.js:177 · 199 · 222 · 253`)을 없앤다.
- 관리 → 매장 설정 → 매장 정보에 **지금 화면 크기**(예 `1024×600`)를 작게 표시한다. 매장 포스에서 실제 표시 영역을 읽기 위한 것이다(10절 6번).
- 검사 상향: `smoke-pos-management.cjs:30`의 48px → 52px.
- 완료 기준: 셸 요소(레일·헤더·필터 줄·하단)에서 ①④ 0건(포스 4개 크기), 기존 검사 통과, 번들 크기 기록.

### M2 · 카드와 쪽 나눔 → 목록 6화면 (L)

- 고칠 곳: `pos-shell.js`(`card :76`, `cards :91`, `pager :103`, `pos-page-change :129`), `pos-shell.css:93~159`, `pos-orders.js`(`cardOf :95`, `listing :124`), `pos-tickets.js`, `pos-dispatch.js`(`taskCard :18`).
- 카드 v4(2-4)와 `P.fit`, 높이 쪽 나눔, 제목 한 줄 규칙, 하단 바 쪽수. 카드의 말줄임표 규칙 5곳(`pos-shell.css:113 · 122 · 125 · 149 · 155`)을 없앤다.
- 카드에 상태 칩은 하나만 둔다. 품목마다 상태가 다르면 가장 급한 것을 보인다(지급 전 → 발권 예정 → 차량 수거 예정 → 대여 중 → 차량 보관 → 반납 완료). 금액도 한 가지(미수 → 예약 금액 → 보증금 → 수납 완료)만 보이고 나머지는 접수 상세에서 본다(10절 3번).
- 열 수는 목록 영역 폭으로 정한다(1024는 2열, 1366은 3열).
- 완료 기준: 접수·준비·이용·반납·리프트권·차량 운행에서 ①~⑤ 0건. 자료 세 가지로 확인한다: 기본 체험 자료, 내일 100팀·긴 이름, 12종 품목.

### M3 · 오늘 할 일 · 정산·마감 (M)

- 고칠 곳: `pos-orders.js home() :143~187`, `pos-finance.js closing() :62`.

- 정산·마감은 왼쪽 수납 대기 행 + 오른쪽 `오늘 마감 준비`. 시안의 48px 행 + 44px `수납` 버튼은 누르는 곳 기준(52px)에 못 미치므로 **행 전체를 누르는 곳으로(52px)** 만든다. 1024×600의 목록 영역은 약 392px이다(카드 목록 실측 · `docs/38` 7-4). 왼쪽 패널에 제목 줄(약 34px)을 두면 6행(312px)까지만 들어가고, 제목 줄을 빼면(건수·금액은 필터 칩과 하단 요약에 이미 있다) 7행(364px)이 들어간다. 계산값이므로 M3에서 실제 크기로 재서 확정한다(10절 4번).
- 완료 기준: 1024×600에서 두 화면 모두 스크롤 없이 ①~⑤ 0건.

### M4 · 새 접수 · 일행·장비 추가 · 접수 상세 (L)

- 완료 기준: 위 검증 스크립트 통과(흐름이 바뀐 곳은 같은 커밋에서 수정), 30명 단체·12종 품목 촬영 통과, ①~⑤ 0건.

## 6. 확인 방법

단계마다 아래를 돌린다. Pages CI는 업무 규칙 검사와 문법·빌드만 돌고 **화면은 전혀 확인하지 않으므로**, 화면 검사는 로컬에서 직접 돌려야 한다.

```bash
npm run check && npm run test:returns && npm run test:notifications && npm run test:workflows:unit
```

```bash
npm run dev
```

서버가 뜬 뒤 다른 터미널에서:

```bash
npm run test:pos:operating && npm run test:pos:fulfillment && npm run test:pos:tickets && npm run test:pos:management && npm run test:pos:preinput && npm run test:pos:keypad && npm run pos:rules
```

```bash
npm run build && npm run pos:screens:driver
```

| 확인 | 기준 |
|---|---|
| 기계 검사 다섯 가지(①~⑤) | 해당 단계 범위에서 0건 |
| 자료 | 기본 체험 자료 · 내일 100팀(긴 이름) · 12종 품목 · 30명 단체 · 긴 장소 |
| 기존 업무 검사 | M0 기준선에서 통과하던 것은 계속 통과 |
| 번들 크기 | 1,750,000 미만(목표 1,650,000 이하), 단계마다 기록 |
| 눈으로 | 단계가 끝나면 주요 화면을 세션에 띄우고 촬영본 모음을 갱신 |
| 실물 | 매장 포스·기사 기기에서 글자 크기와 누르는 느낌 확인(자동화 불가 · M3 이후 1회, M8에 1회) |

## 9. 브랜치와 반영

- Pages는 `main`에 푸시하면 배포된다(체험판 · 저장은 브라우저 메모리). 운영 서버와는 별개다.
